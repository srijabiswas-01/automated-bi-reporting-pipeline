# Readable references without changing UUIDs

Before its first workbook backfill, the updater creates one spreadsheet copy named `Superstore backup before display codes ...` and saves its ID in Script Properties as DISPLAY_CODES_BACKUP_ID. It does not change the original spreadsheet ID. Backups are not deleted automatically.

Business records have permanent display-code columns: customer_code (CUS-0001), product_code (PRD-0001), supplier_code (SUP-0001), order_code (SO-000001), po_code (PO-000001), and corresponding codes for categories, brands, segments, roles, stores, users, addresses, price history, goods receipts, stock movements, payments, shipments, returns and refunds. UUID primary keys, foreign keys, audit references, financial values and stock quantities retain their existing meanings.

Google Sheets remains the authority that assigns codes. The first updated portal or scheduled exporter request recognizes legacy headers, reserves code ranges in Script Properties under the script-wide lock, assigns missing codes, increases those existing records' versions/updated_at values, adds a migration audit summary, then commits through the existing redo journal. New records get codes before their first commit. Master forms cannot supply or edit codes. Gaps after failed operations are intentional; reserved codes are not reused. Inactive records retain their codes. Do not delete DISPLAY_COUNTER_* properties, reset code fields or manually edit IDs/headers.

snapshot_ accepts legacy headers only when the difference is the known additive display-code column. Other header changes are rejected. A prepared pre-upgrade journal can still be replayed, then missing codes are assigned. upgradeDisplayCodes is an optional administrator editor function to run the migration immediately; normal requests perform the same upgrade once. No repeated per-record form entry is required.

Neon receives nullable unique columns before the Sheet migration. ETL also applies that additive schema change under its existing writer lock. Older exported snapshots remain valid with missing codes interpreted as NULL. Once Sheets assigns codes and advances source versions, the next snapshot/ETL fills the code columns. The migration does not rename any keys or rewrite relationships, and older versions cannot overwrite updated rows. No reload, truncation or delete is required.

The portal shows codes first, hides the corresponding UUID primary-key column in normal tables, resolves foreign keys to codes and names, and shows readable references in save confirmations. Detailed record views and raw CSV exports retain UUIDs for technical traceability. Transaction line numbers retain their original numbering.

Deployment order: publish the compatible ETL/model, add Neon columns, upload the updated Apps Script files together while preserving the live manifest, and update the current web-app deployment to that version. Refresh the portal (or wait for its next scheduled export) to migrate the workbook. Check the next GitHub run, and query customer_code/product_code in Neon. Do not restore the old Apps Script code after the workbook upgrade; roll forward with compatible code instead.
